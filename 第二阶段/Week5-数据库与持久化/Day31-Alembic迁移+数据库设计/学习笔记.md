## 一、为什么需要数据库迁移？

**问题场景：** 你写了一个用户管理系统，上线后用了一阵子。现在老板说："加一个手机号字段吧。"

不用 ORM 迁移工具的做法：
```sql
ALTER TABLE users ADD COLUMN phone TEXT;
-- 如果字段要非空呢？得先 add NULL → 再 UPDATE 填充默认值 → 再改成 NOT NULL
-- 多条 SQL，手动手残删库的风险极高
```

用 Alembic 的做法：改一行 Python 代码 → 自动生成分享文件 → `alembic upgrade head` → 搞定。

**类比理解：** 把数据库迁移想象成 Git 管理代码——
```
代码演进 → git commit → 回滚 → git revert
数据库演进 → alembic revision → downgrade → 随时回退
```

每次改表结构都生成一个「迁移脚本」(migration script)，这些脚本串联起来就是 migration chain（迁移链）。你可以沿着链前进（upgrade），也可以后退（downgrade）。

## 二、Alembic 初始化

### 2.1 安装

```bash
pip install alembic
```

Alembic 不依赖 SQLAlchemy，但配合 SQLAlchemy 使用最方便。

### 2.2 初始化项目

进入你的项目根目录，执行：

```bash
alembic init alembic
```

这会在当前目录下创建一个 `alembic/` 文件夹，包含三个核心文件：

| 文件 | 作用 |
|------|------|
| `alembic.ini` | Alembic 的主配置文件，类似 .env，里面存数据库连接字符串 |
| `env.py` | 迁移执行时的环境脚本，告诉 Alembic "模型类在哪里" |
| `versions/` | 存放所有生成的迁移脚本的文件夹 |

### 2.3 配置 sqlalchemy.url

编辑 `alembic.ini`，找到这一行：

```ini
sqlalchemy.url = driver://user:pass@localhost/dbname
```

改成你的数据库连接字符串：

```ini
sqlalchemy.url = sqlite:///./app.db
```

如果是 SQLite 文件，写法是 `sqlite:///./文件名.db`。

### 2.4 配置 env.py

编辑 `alembic/env.py`，找到 `target_metadata` 部分：

```python
from your_app.models import Base    # ← 导入你的 Base 基类
target_metadata = Base.metadata      # ← 让它引用你的模型元数据
```

然后在 `run_migrations_online()` 函数中取消注释以下两行：

```python
with connectable.connect() as connection:
    context.run_migrations(connection)   # ← 确保这两行没有被注释
```

还需要在文件顶部添加 `import sys` + `sys.path.insert()`，让 Python 能找到你的模型模块：

```python
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).parents[1]))  # 指向项目根目录
```

**常见坑：** 路径不对导致 "ModuleNotFoundError: No module named 'models'"。排查方法是在 env.py 里打印 `sys.path`，确认能搜到你的模型文件。

## 三、自动生成迁移脚本

当你修改了 SQLAlchemy 模型类（加了列、改了类型、加了外键等），可以告诉 Alembic 自动生成对应的迁移脚本：

```bash
alembic revision --autogenerate -m "add user table"
```

参数说明：
- `--autogenerate`：对比当前模型定义和数据库现状，自动生成差异脚本
- `-m "xxx"`：描述信息，会写入生成的迁移脚本文件中

**它会生成什么？** 类似于 `versions/001_add_user_table.py` 的文件：

```python
def upgrade():
    op.create_table('users',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('username', sa.String(length=50), nullable=False),
        sa.Column('email', sa.String(length=100), nullable=True),
        sa.PrimaryKeyConstraint('id'),
    )

def downgrade():
    op.drop_table('users')
```

`upgrade()` 是正向操作（建表），`downgrade()` 是反向操作（删表）。

### autogenerate 的能力边界

| 能做 | 不能做（需要你手动改） |
|------|---------------------|
| 新增表 | 修改列名（rename column）|
| 新增列 | 修改列类型（Integer → String）|
| 删除列 | 删除列 |
| 添加 NOT NULL 约束 | 删除表 |
| | 修改 ForeignKey |

**重要提醒：** Alembic 的 autogenerate 不是万能的！简单变化它能识别，复杂变化需要你打开生成的 `.py` 文件手动修正。这是新手最容易踩的坑。

## 四、执行迁移

### 升级（apply 最新的迁移）

```bash
alembic upgrade head
```

`head` 表示迁移链的最新版本。这会把所有未执行的迁移脚本按顺序跑一遍。

执行后，数据库里会自动创建一个 `alembic_version` 表：

```sql
CREATE TABLE alembic_version (
    version_num TEXT NOT NULL
);
-- 记录当前数据库处于哪个迁移版本
```

查看当前版本：

```bash
alembic current       # 显示当前数据库的版本号
alembic history       # 显示所有迁移历史的链条
```

### 验证迁移效果

```python
import sqlite3
conn = sqlite3.connect("app.db")
cursor = conn.cursor()
cursor.execute("SELECT name FROM sqlite_master WHERE type='table'")
print(cursor.fetchall())
# 输出：[('alembic_version',), ('users',)]  ← 可以看到 alembic 自动建的版本表
conn.close()
```

## 五、回滚迁移

### 回退一步

```bash
alembic downgrade -1
```

`-1` 表示回退到上一个版本。也可以用具体版本号：

```bash
alembic downgrade 001abcdef            # 回退到指定版本
alembic downgrade base                  # 回退到最初（所有表都没了）
```

### 理解 Migration Chain

```
base ──→ 001 (create users) ──→ 002 (add email to users) ──→ 003 (create posts) ← head
                                              ↑
                                         当前在这里
```

- `upgrade head` → 从当前位置走到最右边
- `downgrade -1` → 回到前一个版本（撤销 003）
- `downgrade base` → 全部撤销（回到裸数据库）

⚠️ **生产环境慎用 downgradel** 一旦回滚，这个版本之后插入的数据都会丢失！

## 六、数据库设计基础：三大范式

范式（Normal Form）是关系型数据库设计的准则，目的是减少数据冗余、避免更新异常。

### 6.1 第一范式（1NF）：每列不可再分（原子性）

规则：每个单元格只能放一个值，不能是列表或 JSON。

✅ 正确的设计：
```
学生表：
| id | name | course | grade |
|----|------|--------|-------|
| 1  | 张三 | 数学   | 90    |
| 1  | 张三 | 英语   | 85    |
```

❌ 违反 1NF 的设计：
```
学生表：
| id | name | courses_grades     |
|----|------|--------------------|
| 1  | 张三 | [数学:90, 英语:85] |
```

为什么不行？你没法写 SQL 查询"找出数学成绩高于 90 的学生"，因为整个 `[数学:90, 英语:85]` 是一个整体，不是独立可查的字段。

### 6.2 第二范式（2NF）：没有部分依赖

规则：在非主键列必须完全依赖于整个主键（不能有"只依赖于主键的一部分"的情况）。

反面案例：
```
订单明细表：
| order_id | product_id | product_name | quantity | unit_price |
|----------|------------|--------------|----------|------------|

复合主键：(order_id, product_id)
问题：product_name 和 unit_price 只依赖于 product_id，跟 order_id 没关系
```

优化后的拆分：
```
订单表：           | 产品表：            | 订单明细表：
| order_id | ...   | | product_id | name | | order_id | product_id | qty |
|----------|-------| |------------|------| |----------|------------|-----|
```

### 6.3 第三范式（3NF）：没有传递依赖

规则：非主键列之间也不能互相依赖（A→B→C，C 只依赖 A 而不直接依赖主键）。

反面案例：
```
员工表：
| emp_id | name | dept_id | dept_name | dept_location |
|--------|------|---------|-----------|---------------|

dept_name 依赖于 dept_id，而 dept_id 依赖于 emp_id
这就叫传递依赖：emp_id → dept_id → dept_name
```

优化后拆分：
```
员工表：          | 部门表：
| emp_id | name | | dept_id | dept_name | location |
|--------|------| |---------|-------------|----------|
```

### 6.4 实际开发中的取舍

规范是理想状态，实际工程中经常适度违背范式来换性能：
- **反范式化**：故意冗余一些字段（如在订单表里冗余用户名字段），减少 JOIN 次数
- **读写分离**：读多写少的场景允许一定程度的数据重复
- NoSQL 数据库天然不追求范式，因为它们处理的是半结构化数据

对于学习阶段：理解前三范式足以应付 90% 的场景。

## 七、索引：加速查询的代价

### 7.1 什么是索引？

索引就像书的目录——有了目录你能快速翻到某一页，不需要从头到尾逐页翻找。

数据库索引通常用 **B+ 树** 实现：

```
              [20]
             /    \
       [5,10]     [30,40]
       / | \      /   |   \
     [2][8]    [25][35][45]

查找 ID=35 时：只需比较 3 次（log₂8 ≈ 3）
如果不建索引：可能需要比较 8 次（线性扫描）
数据量越大，优势越明显
```

### 7.2 什么时候该加索引？

- 频繁出现在 `WHERE` 条件中的字段
- 频繁用于 `ORDER BY` 排序的字段
- 频繁用于 `GROUP BY` 分组计算的字段
- 外键字段（JOIN 关联时用）

### 7.3 什么时候不需要索引？

| 场景 | 原因 |
|------|------|
| 小表（几百条以内） | 全表扫描比走索引更快 |
| 低基数字段（如性别、状态开关） | 区分度太低，索引效果差 |
| 大量更新的表 | 索引本身也需要维护，更新时会减慢 INSERT/UPDATE |

### 7.4 复合索引的最左前缀原则

```sql
-- 创建复合索引 (first_name, last_name, age)
CREATE INDEX idx_name ON users (first_name, last_name, age);

-- ✅ 可以用索引：先匹配 first_name
SELECT * FROM users WHERE first_name = '张';

-- ✅ 可以用索引：先 first_name 再 last_name
SELECT * FROM users WHERE first_name = '张' AND last_name = '三';

-- ❌ 不能用完整索引：跳过了 first_name
SELECT * FROM users WHERE last_name = '三';
-- （SQLite 可能会退化到全表扫描）
```

类比：就像查电话号码簿——你先知道姓氏才能查到名字，不知道姓氏就无从下手。

### 7.5 EXPLAIN ANALYZE — 看 SQL 怎么跑的

```sql
EXPLAIN ANALYZE SELECT * FROM todos WHERE category = '学习';
```

输出示例：
```
SEARCH TABLE todos USING INDEX idx_category (category=?)(rowid > 0)
Execution time: 0.3 ms
```

如果没有用索引：
```
SCAN TABLE todos
Execution time: 15.2 ms
```

看到 `SCAN` 就要警惕了——说明在做全表扫描，考虑加索引。
