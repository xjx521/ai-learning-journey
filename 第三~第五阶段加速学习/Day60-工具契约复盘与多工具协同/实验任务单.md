### 实验 B：多工具协同【提示】★★

**概念**：真任务往往要"**依次调多个工具**"。模型每调一个工具，结果作为 Observation 拼回 messages，它才能决定下一步调什么。这是 Agent 和 FC 的本质区别（Day58 笔记第1节：FC 只发一次调用，Agent 自动循环到完成）。

**步骤**（提示级，不给代码）：
1. 在实验 A 的 TOOLS 里加两个文件工具（`save_note` / `read_note` 的**普通函数版**，复用 Day59 exp_b 的 `_safe_path` + 逻辑，去掉 `@tool`）
2. 跑多步任务："帮我查北京天气，然后把天气记到 note.txt"
3. 观察：模型调了几次工具？顺序对不对？（应该 `get_weather` → 拿到 Observation → `save_note`）第二次调用时它"记得"第一次的结果吗？（提示：Observation 已经拼回 messages）
4. 再问"我刚才记的什么？"——看它会不会调 `read_note` 读回并转述（Day59 实测：读回成功但 7B 模型没转述，今天**再验证一次**，对比两次结果）
5. 填观察表

### 实验 C：破坏性对照【提示】

**概念**：工具契约的坑在真实场景全踩一遍，才知道生产怎么加固。

**步骤**（提示级，不给代码）：
1. **description 写糊**：把 get_weather 在 SYSTEM 里的描述故意写错（"get_weather(城市名) 查询城市**空气质量指数**"）→ 问"北京天气怎么样"→ 看模型会不会被误导（选错工具 / 参数填错）。对比写对时的表现
2. **工具太多挑花眼**：一次给 8 个工具（真 3 个 + 凑数 5 个无关的，如 get_poem / get_stock / get_news...）→ 问"现在几点"→ 看 7B 模型会不会犹豫/选错 → 缓解：**工具过滤**（根据任务只把相关的 2-3 个给模型）
3. **对照 raw vs @tool**：同一只 get_weather，raw 版（SYSTEM 文本描述）和 @tool 版（自动 schema）各测一次"北京天气"，哪个解析参数更稳？（Day59 自评结论"@tool 更稳"今天用数据验证）
