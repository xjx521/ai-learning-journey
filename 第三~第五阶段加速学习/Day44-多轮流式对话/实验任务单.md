## 二、动手实验（3-4 小时，核心）

### 实验 A：多轮对话——模型真的"记得"吗？（约 1 小时）★
写 `chat_multi.py`：
1. 第一句：`{"role": "user", "content": "你好，我叫小明，我住在北京"}`，打印回答
2. 把第一轮 messages **原样拼上** assistant 的回答，再加第二句：`{"role": "user", "content": "我叫什么名字？我住在哪？"}`，**整段发过去**，打印回答

| 轮次  | messages 里装了什么                     | 模型回答                                                         |
| ----- | --------------------------------------- | ---------------------------------------------------------------- |
| 第1轮 | 只有"我叫小明…"                         | 你好，小明！很高兴认识你～北京是个好地方。有什么我可以帮你的吗？ |
| 第2轮 | 第1轮全部 + assistant 回答 + "我叫什么" | 你叫小明，住在北京～没错吧？😊                                    |

**破坏性对照（关键）**：第 2 轮**只发**"我叫什么名字？"，不带历史——看它还能答对吗？

| 第2轮(不带历史) | messages 只装新问题 | 模型回答 |
| "我叫什么名字？我住在哪？" | "我叫什么名字？我住在哪？"| 对不起，我不知道你的名字和住址。你没有告诉我这些信息哦。你可以告诉我，我就记住了！|

观察思考：两种方式答案一样吗？这证明了什么？
不一样 证明了大模型是没有记忆的 所有的记忆只是来源于把所有对话上下文在本次请求时发过去
### 实验 B：流式输出——打字机效果（约 1 小时）★★
写 `chat_stream.py`：
- 在 `create()` 里加 `stream=True`
- 用 `for chunk in response:` 循环，每拿到一小块就 `print(chunk.choices[0].delta.content, end="")` 立即打印（不换行）
- 感受：文字是**一个字一个字蹦出来的**，不是等全部生成完才一次性出来
- 对照：再跑一次不加 stream 的，对比"整段蹦出" vs "打字机"

观察思考：流式收到的一小块 chunk 大概是多大？是一整个词吗？（试着在每块后面打印个标记符看看粒度）
不是一个词是一个token有可能2-3词
### 实验 C：system 角色 + 长对话成本观察（约 1 小时）★★
写 `chat_system.py`：
1. 带 system：`{"role": "system", "content": "你是客服小助手，回答必须简短，不超过20个字"}`，然后连问两句，观察回答风格
2. **破坏性对照**：不传 system、只传 user，同样的问题，对比风格差异
3. **成本观察（呼应 Day43 上下文窗口）**：每一轮打印 messages 里文本总长度 `len(str(messages))`，连续聊 5 轮，看它是不是**越来越长** → 每轮请求花的 token 越来越多 → 这就是"长对话烧钱"的原因

| 轮次 | 带system回答                          | 不带system回答                        | messages文本长度 |
| ---- | ------------------------------------- | ------------------------------------- | ---------------- |
| 1    | 第1次回答: 你好，请问有什么可以帮你？ | 第4次回答: 好的，我会简短回答         | 1                |
| 2    | 第2次回答: 好的，请问有什么可以帮您？ | 第5次回答: 好的，请问有什么可以帮您？ | 6                |
| 3    | 第3次回答: 您好，请问有什么可以帮您？ |                                       | 7                |

## 三、自测 5 关（晚上对着自查）
- **能讲**：一句话向同学解释"为什么多轮对话每次都要把历史 messages 发过去"
  - 因为大模型本身没有记忆 每次请求都把上下文历史传过去才能让他了解你
- **能写**：不查资料写出 system / user / assistant 三种 role 各自用途
  - system系统规则 user用户 assistant AI助手
- **能修**：报错提示 messages 里缺 role 字段 / content 不是字符串，你知道去哪查、怎么改
  - 去message里面检查role字段是否有空格或者其他原因 content位置加上双引号
- **能答 why**：为什么说 LLM API 是"无状态"（stateless）的？这和网页聊天能"记住"你矛盾吗？
  - 不矛盾 因为LLM本身是无记忆的 网页聊天能记住你是你在发送本次请求时把上下文历史传过去了 ai通过了解上下文历史来记住你
- **能扛边界**：连续聊了 100 轮，messages 越来越长、快超上下文窗口了，你会怎么处理？写出 2 种思路
  -1.我会在上下文快到ai幻觉之前大概占用率（70%-80%）前，让AI写一个交接文档记住关键信息，然后新开一个messages，让ai重新阅读该交接文档
  -2.截断历史最久的messagess
  -3.RAG：把旧对话记录存入向量数据库 不占用上下文窗口 聊天时按需求检索数据库关键词再把关键信息存入prompt 上下文只存近期对话
