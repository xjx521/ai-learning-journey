## 一、概念预习（约 1.5 小时）——先看课，不迷茫

### 第一步：看吴恩达 RAG 课（集号已记入 CLAUDE.md）
- **P19 近似最近邻(ANN)算法** ★核心：为什么向量库检索快（索引 + 近似，牺牲少量精度换数量级提速）
- ANN 在入库构建索引，检索仅查询局部区域，牺牲少量精度换取速度提升；HNSW 是经典 ANN 图索引算法，基于贪心搜索，采用多层图结构：上层长距离连接粗定位，底层稠密连接精细检索，向量作为节点互相连线，最终取出近似 TopK 近邻
- **P20 向量数据库技术** ★核心：向量数据库解决什么、和普通数据库啥关系
  - 向量数据库持久存储向量，避免程序重启重复计算 embedding，并且内置 ANN 索引实现快速语义检索；普通数据库擅长结构化精确查询，不适合海量高维向量的相似度匹配。
- **P21 文本分块技术** ★核心：为什么文档要切块、chunk_size 怎么定
  - 完整文档过长，直接处理会造成语义稀释，还容易超出模型输入长度限制，因此需要切块。chunk_size 常用方案包括固定长度、滑动重叠分块、LLM 辅助分块、向量语义分块。
- **P22 高级分块方法论**：分块策略对检索质量的影响（了解）
  - 基础的固定长度、分隔符分块容易切断完整语义，造成 chunk 上下文残缺；滑动窗口补齐上下文会带来文本冗余，影响检索质量。高级分块会按照语义边界切分，保障片段语义独立完整
- **P11 元数据过滤技术** ★核心：metadata 是什么、检索前先过滤
  - metadata是元数据和文本向量绑定存储的结构化键值标签，例如文档年份、部门、来源、权限等级、文档类型、年份等业务属性 元数据过滤就是先过滤元数据标签再做向量检索 比如数据库select.where year=2026

### 实验 A：认识 ChromaDB（新概念 →【示例】，只看懂长什么样）

ChromaDB 是全新的库，API 结构和手写 list 完全不同，给最小可跑示例。搞清 4 个动作：**建库 → 建 collection → add 存文档 → query 查**。

```python
# 实验 A：认识 ChromaDB（第一次接触向量数据库）
import chromadb
from chromadb import Documents, EmbeddingFunction, Embeddings
from openai import OpenAI

# 把 Day51 的 get_embedding 包成 ChromaDB 的接口：
# __init__ 里存好客户端（只建一次），__call__ 一次性把一批文字批量变向量
class OllamaEmbeddingFunction(EmbeddingFunction[Documents]):
    def __init__(self):
        self._client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")

    def __call__(self, input: Documents) -> Embeddings:
        resp = self._client.embeddings.create(model="bge-m3", input=list(input))  # 一批文字一次调用
        return [r.embedding for r in resp.data]

# ---- 2. 建库（PersistentClient = 持久化，数据落盘到文件夹）----
client = chromadb.PersistentClient(path="./chroma_data")  # 数据会存到这个文件夹

# ---- 3. 建 collection（相当于"一张表"，embedding_function 告诉它怎么把文字变向量）----
col = client.get_or_create_collection(
    name="hr_policies",          # collection 名字，随便起
    embedding_function=OllamaEmbeddingFunction(),  # 用本地 bge-m3，不额外下载模型
)

# ---- 4. 存文档（add：ids 唯一编号 + documents 内容）----
col.add(
    ids=["doc1", "doc2"],
    documents=[
        "年假政策：入职满一年有5天年假，满三年10天，满五年15天。",
        "薪酬发放：每月15号发放上个月的薪水，遇节假日提前到最近的工作日。",
    ],
)
print("库里现有文档数:", col.count())  # 2

# ---- 5. 查（query：只传 query_texts，数据库自动 embedding 问题向量，再 ANN 搜最近的）----
res = col.query(query_texts=["我入职两年有几天年假？"], n_results=1)
print("命中:", res["documents"][0])   # ['年假政策：...']
print("距离:", res["distances"][0])   # 越小越近（ChromaDB 默认 L2 距离，不是余弦！）
```

**留空记录表格**：
| 动作          | 我预想的 API                      | 实际 API                                             | 备注           |
| ------------- | --------------------------------- | ---------------------------------------------------- | -------------- |
| 建库          | 没学没想过其写法                  | `PersistentClient(path=...)`                         | 数据落盘       |
| 建 collection | 没学没想过其写法                  | `get_or_create_collection(name, embedding_function)` | 相当于表       |
| 存文档        | col.add(documents)没想到ids也要存 | `col.add(ids=[], documents=[])`                      | 自动算向量     |

- **观察思考**：`col.query` 只传了问题文字，没传向量——向量谁算的？（ChromaDB 调了 embedding_function）。对比 Day51 你手写版每 query 算 6 次文档向量——ChromaDB 的文档向量是不是只算了 1 次？（add 时算的）这 1 次 vs 24 次就是"向量存库"的价值。
    向量数据库在建表时调用了embedding_function在里面调用了模型算向量 是的在add是否就算了一次以后每次只需要在向量数据库中检索即可

- **能讲**：向量数据库存的是什么？ANN"近似"搜近似在哪？为什么文档向量要算一次存起来？

- **能写**：默写 ChromaDB 最小四件套（PersistentClient / get_or_create_collection / add / query）
- chroma.PersistentClient(path="")get_or_create_collection(namae="",embedding_function=OllamaEmbeddingFunction()) col.add(ids=["d1",document=knowledge],medata=) col.query(query_text=[""],n_result=2,where=)
- **能修**：query 返回空/结果不对，先查哪几处？（Ollama 服务在不在 / embedding_function 对不对 / collection 里到底存了什么 `col.count()` / metadata 过滤条件写对没）
  - 1.模型服务打开了吗2.embedding_function写对了吗3.collection存了啥有没有重复存储(改update) 4.过滤条件写对了吗
- **能答 why**：为什么用 L2 距离而 Day51 用余弦？两者排序一定一样吗？为什么 ChromaDB 不用每次重算文档向量？
  - L2 距离和余弦相似度的排序结果**不一定完全一致**。向量数据库底层 ANN 索引（如 HNSW）常基于 L2 距离构建，适配索引遍历、节点比对的检索逻辑；余弦侧重衡量向量方向夹角，适合只关心语义方向、不关心向量模长的场景。
ChromaDB 预先将文档向量持久化存入数据库，文档入库阶段只计算一次 embedding，后续检索复用已有向量，不需要重复计算文档向量。
- **能扛边界**：ChromaDB 默认 search 也是近似（HNSW 索引），什么情况下"近似"会漏掉正确答案？metadata 过滤和分块分别是为什么而存在的？
   HNSW 索引以向量作为**节点**，检索只遍历部分相连节点；若目标节点不在检索路径内，近似检索会漏掉正确答案。
metadata 过滤：提前筛选候选节点；分块：拆分长文本，构建细粒度节点，优化召回精度。
