## 一、概念预习（约 1.5 小时）——先看课，不迷茫

### 第一步：看吴恩达 RAG 课（集号已记入 CLAUDE.md）
- **P13 关键词搜索：BM25 算法** ★核心：Day50 字符重叠的"正规军升级"
  - BM25 用 TF-IDF 思想：**IDF**（这个词在越少文档里出现，撞上越值钱）+ **TF 归一化**（同一词出现太多次，价值递减；长文档被惩罚）。经典参数 k1=1.5、b=0.75。
  - TF 词频 IDF：词语出现的文档越少，权重越高；k1 参数：对 TF 词频做饱和归一，同一个词多次出现分数不再疯狂上涨；b 参数：对长文档施加惩罚，消除文档长度带来的不公平。
标准默认参数：`k1=1.5，b=0.75`
- **P16 混合搜索策略** ★核心：为什么单一检索有盲区、怎么融合
  - 关键词检索强在精确词，语义检索强在意思。混合 = 两个都搜，把两份排名合成一份。常见融合法：**RRF（Reciprocal Rank Fusion）**——只看"名次"不看"分数"，天然绕开不同检索器单位不同（L2 距离 vs BM25 分）的问题：`score(d) = Σ 1/(60 + rank)`。
- **P23 查询语句解析**（了解）：把一句话查询拆成"该走关键词的部分 + 该走语义的部分"——混合检索的进阶版，今天只要知道有这回事
  - ### 举个例子
    用户提问：`"政策编号HR‑003，入职之后年假怎么计算？"`
    - 关键词部分：`HR‑003`（编号，交给 BM25，要精确命中）
    - 语义部分：`入职之后年假怎么计算`（交给向量语义检索）
  
- **P24 交叉编码器与ColBERT 模型** ★核心：**bi-encoder vs cross-encoder**
  - **bi-encoder（Day51/52 用的）**：query 单独算一个向量、doc 单独算一个向量，再算余弦。**快**（向量可以提前算好存库，支持百万级），但粗——它俩从头到尾没"见过面"。
  - **cross-encoder**：把 query 和 doc 拼在一起喂进模型，让模型看到两者的**交互**。准，但慢（只能对几十个候选重排，没法对全库）。
  - ColBERT = 中间路线（每个 token 都编码 + 后期交互），了解即可。
  - ColBERT 是延迟交互检索模型，**不为文档生成单个向量，而是每个 token 输出独立向量**；
采用 MaxSim 打分：查询每个 token 在文档 token 集合中找最大相似度，全部求和得到文档分数。
文档向量可以离线预计算。效果介于普通单向量检索和 Cross‑Encoder 重排器之间；代价是存储量大，工程一般用来做精排。

- **P25 检索结果重排序技术** ★核心：**两阶段管道**
  - 召回（retrieval）：bi-encoder 快速从全库捞 top-K（K 大点，比如 20/50，宁可多捞点噪音）；
  - 重排（rerank）：cross-encoder 只对 top-K 精排，把真正相关的顶上 → 取 top-2/3 进生成。
  - **为什么不能只做其中一步**：只召回不重排 → top-K 里有噪音，进 prompt 干扰回答；只重排不召回 → cross-encoder 对全库跑太慢。

### 实验 A：手写 BM25 关键词打分（P13，新概念 →【示例】只看懂公式长什么样）

Day50 的 `char_overlap_score` 是"数撞了多少字"，每个字一样重要。BM25 是正规军：**稀有字撞上更值钱（IDF）+ 同字重复价值递减（TF 归一化）+ 长文档被惩罚**。公式是今天唯一的新数学，给完整【示例】带注释——只看懂，别背：

```python
# 实验 A：手写 BM25 关键词打分（P13）
from math import log
from collections import Counter

# ---- 0. 中文分词：没有空格，先用"每个字一个 token"（字符级）----
def tokenize(text):
    return list(text)                      # "报销规则" -> ['报','销','规','则']

# ---- 1. 每篇文档的词频 TF（token 在文档里出现几次）----
docs = [
    "薪酬发放：每月15号发放上个月的薪水，遇节假日提前到最近的工作日。",
    "年假政策：入职满一年有5天年假，满三年10天，满五年15天。",
    # ... 6 段知识库原样搬过来
]
doc_tfs = [Counter(tokenize(doc)) for doc in docs]   # 每段文档一个 Counter

# ---- 2. 逆文档频率 IDF（这个 token 在几篇文档里出现过？越少越值钱）----
N = len(docs)
doc_freq = {}                                # token -> 出现在几篇文档里
for tf in doc_tfs:
    for token in tf:
        doc_freq[token] = doc_freq.get(token, 0) + 1
idf = {t: log(1 + (N - df + 0.5) / (df + 0.5)) for t, df in doc_freq.items()}

# ---- 3. BM25 打分公式（k1=1.5, b=0.75 经典默认值）----
#   score(d,q) = Σ_{query里的每个字}  IDF * tf*(k1+1) / (tf + k1*(1-b + b*len(d)/avgdl))
#   直觉：tf 越大分越高但"递增变慢"；len(d) 越长分被拉低（惩罚又长又重复的文档）
def bm25_score(query, doc_tf, doc_len, avgdl, idf, k1=1.5, b=0.75):
    score = 0.0
    for token in tokenize(query):
        if token not in idf:
            continue                          # query 的字全库没见过，跳过
        tf = doc_tf.get(token, 0)
        if tf == 0:
            continue
        denom = tf + k1 * (1 - b + b * doc_len / avgdl)
        score += idf[token] * (tf * (k1 + 1)) / denom
    return score
```

**你的任务（【提示】，打分+排序你写过两遍了）**：
1. 算 `avgdl = 所有文档字数 / N`（字符级分词后就是 list 长度）
2. 对**每篇文档**算一次 `bm25_score(query, ...)`，套 Day50 的"打分 → 排序 → top_k"套路，取 top_1
3. 用 Day51 的 4 个问题（年假/工资/放松/团建）各跑一遍，对比 Day50 字符重叠的结果

### 实验 C：重排序——两阶段管道的第二段（P24/25，【骨架】）

概念：**召回快而粗 → 重排慢而准**。本地没装 cross-encoder（要 torch），我们用 **DeepSeek 当重排器**——它和 cross-encoder 一样是"把 query 和所有候选放在一起看"（交互式），比 bi-encoder 的"分开看"准。这是真实生产技术（LLM-as-reranker）。

**【骨架】重排 prompt（新东西是"让模型输出排序"的格式，prompt 给你，逻辑你填）**：
```python

# 步骤2：把 query + 5 段带编号的候选塞给 DeepSeek，要求只输出排序
RERANK_PROMPT = """你是检索重排器。下面是查询和 5 段候选资料。
只输出按"相关性从高到低"排序的编号，格式如 [2,1,4,3,5]，不要解释。

查询：{query}
候选：
[1] {doc1}
[2] {doc2}
[3] {doc3}
[4] {doc4}
[5] {doc5}"""
# 步骤3：解析模型输出的 [..]，取前 2 名，作为"重排后的 top-2"
```

- **能讲**：为什么单一检索有盲区？RRF 是什么、为什么用名次不用分数？bi-encoder 和 cross-encoder 差在哪？
- BM25 抓字面实体，bi‑encoder 向量抓语义，两者多路召回；因为两路分数不能对比，用 RRF 按名次融合候选；最后用 cross‑encoder 做高精度重排，过滤掉噪声，再送入 LLM。
- **能写**：默写 BM25 打分公式（IDF + TF 归一化的样子）+ RRF 公式
- RRF：1/(60+rank_bm25)+1/(60+rank_vec) BM25:denom=tf+k1*(1-b+b*doc_len/avgdl) score+=(idf[token]*(tf*(k1+1)))/denom  idf={t:l;og(1+(N-df+0.5)/(df+0.5))}
- **能修**：BM25 打分全是 0，先查哪几处？（tokenize 对没对 / idf 字典有没有值 / query 的字全库没见过？）
tokenize有没有正确的字写对了吗 idf字典有没有值 query的字全库都找不到吗
- **能答 why**：为什么不能只召回不重排、只重排不召回？为什么不用"BM25 分数 + 余弦分数"直接加，要用 RRF？
- 只召回不重排遇到大的知识库噪音大检索质量不过关 只重排不召回速度慢 所以要通过先召回快速筛选出top_k个文档再用重排筛选出最高的几个文档  两者的打分分布值域完全不一样 分数不具备可比性
- **能扛边界**：1000 万段文档，混合检索会卡在哪一步？（BM25 全遍历打分？向量库 ANN 快但 K 大？重排只能对多少段做？）
1. BM25：如果手写暴力全遍历打分，直接卡死；工程用倒排索引，瓶颈来自高频查询词带来过长倒排拉链。
2. 向量 ANN：本身是近似检索速度快，但 top_k 设置过大会变慢；千万向量索引对内存要求高，落盘会增加延迟；ANN 存在速度与召回精度权衡。
3. Cross‑encoder 重排有严格上限，**只能处理几十到一百多条候选，不能直接面对千万级全量文档**。

> 
> 整体流程：BM25、ANN 负责从千万文档粗筛得到小候选集合，RRF 融合，再交给 cross‑encoder 重排。

## 高频坑（面试容易答错）

❌ 错误：向量库会计算 1000 万次余弦相似度
✅ 正确：ANN 索引避免全量计算余弦，是近似检索。

❌ 错误：cross‑encoder 可以对全部千万文档重排
✅ 正确：cross‑encoder 推理开销大，只能处理前面召回输出的少量候选。

❌ 错误：BM25 每次查询遍历全部 1000 万文档
✅ 正确：依靠倒排索引，只计算查询词命中的文档集合
