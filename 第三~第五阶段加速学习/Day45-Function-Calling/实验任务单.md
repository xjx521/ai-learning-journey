## 二、动手实验（3-4 小时，核心）

### 实验 A：给模型配一个"加法计算器"（约 1 小时）★
写 `tool_add.py`（从 call_deepseek.py 复制骨架）：
- 这个嵌套结构**别硬背**，照着下面填，注释讲清每层是干嘛的：

```python
tools = [
    {
        "type": "function",                 # 固定写法：这是个"函数工具"
        "function": {
            "name": "add",                  # ← 工具名（模型调用时用这个名字）
            "description": "两个整数相加",   # ← 描述：模型靠它决定"要不要用这个工具"
            "parameters": {                 # 参数说明（JSON Schema 格式）
                "type": "object",
                "properties": {
                    "a": {"type": "integer", "description": "第一个加数"},
                    "b": {"type": "integer", "description": "第二个加数"},
                },
                "required": ["a", "b"],     # 必填参数
            },
        },
    }
]
```

- 问「3 加 5 等于几？」，`create()` 里加 `tools=tools`
- **关键观察**：这次模型**不会直接答 8**，而是返回一个 `tool_calls`。记录它长什么样：

| 观察项 | 你看到的实际内容 |
|--------|-----------------|
| 想调用哪个工具（name） | |
| 参数是什么（arguments） | |
| 有没有同时直接给文字答案 | |

### 实验 B：你执行工具，把结果喂回去（约 2 小时）★★ 核心
- 拿到 `tool_calls` 后，**你自己**执行计算（`a + b`），把结果作为 **role="tool"** 的消息发回去，模型这才给出最终答案
- 完整流程（记录每一步的 role 和 content）：

| 步骤 | role | 装的内容 | 谁产生的 |
|------|------|---------|---------|
| 1 | user | "3 加 5 等于几？" | 你 |
| 2 | assistant | tool_calls: add(a=3, b=5) | 模型 |
| 3 | tool | "8" | 你（执行工具后塞回去） |
| 4 | assistant | "3 + 5 = 8" | 模型 |

> 提示：第 2 步的 assistant 消息**要原样 append 回 messages**（带 tool_calls 的那条），第 3 步的 tool 消息里有个 `tool_call_id` 要跟它对应上——这是最容易踩的坑，卡住了贴报错给我。

### 实验 C：现实场景——天气工具 vs 幻觉对照（约 1 小时）★★★
写 `tool_weather.py`：
- 定义一个 `get_weather(city)` 工具，**假装**你有数据库（dict：`{"北京": "晴，28℃", "上海": "小雨，25℃"}`），你执行函数时从 dict 里取真数据
- 问「北京今天天气怎么样？」，走完整三段式
- **破坏性对照（关键）**：把 `tools` 注释掉，直接问「北京今天天气怎么样」——看模型会**怎么编**？

| 有工具 | 模型回答（基于真数据） | 无工具 | 模型回答（编的） |
|--------|----------------------|--------|-----------------|
|        |                      |        |                 |

- 观察思考：无工具时模型回答靠谱吗？→ 这就是**幻觉**现场演示。**Function Calling = 让模型"查了再说"，从根上治幻觉**

## 三、自测 5 关（晚上对着自查）

- **能写**：不查资料写一个最简 `tools` 参数（name / description / parameters 三样）
