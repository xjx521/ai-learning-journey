# 滑动窗口实现逻辑（对应你题目「删掉更早上下文」）

业务标准做法（写进 Agent 代码）：

1. 每次发起 API 调用前，估算 messages 所有 token 数量
2. 如果 `总token + max_tokens > 上下文窗口上限`
3. 持续 `messages.pop(0)` 删除**最最早的一条历史消息**#不删除system 最好删除user和assistant
4. 循环直到整体 token 足够安全
   
### 边读边想的 3 个问题
1. 为什么长对话的 API 账单涨得比"你实际打的字"快？
    因为大模型没有记忆 长对话时会把历史对话加本次对话一起输入 大模型才能了解你 这时候输入token高
2. 输出被截断时，用户看到的是"一句话说一半"——程序怎么知道是截断还是正常结束？（提示：`finish_reason`）
     用条件判断读取finish_reason：if response.choices[0].choice.finish_reason=="stop":正常结束 =="length"：截断

### 四个常见 finish_reason 全部记住

- `"stop"`：模型正常说完，主动停止
- `"length"`：token 上限强制截断（你关心的场景）
- `"tool_calls"`：停止文本，发起工具调用
- `"content_filter"`：内容触发安全审查被拦截
  
1. 上下文窗口满了，为什么不能直接删掉最老的 user 消息？（提示：assistant 的回答也依赖更早的上下文）
    user和assistant回答是成双成对存在的  assistant的回答是基于user的要求产生的 如果只删除user不删除assistant容易引发逻辑混乱造成模型幻觉答非所问，破坏因果关系，function calling结构异常, 所以删除时应该删除一组user+assistant

### 实验 B：max_tokens 截断实验（约 1 小时）★★

任务：把 `max_tokens` 设得极小，观察输出被切断 + `finish_reason` 的变化。

> `max_tokens` 和 `finish_reason` 是今天唯一的新 API 字段，给一次【示例】看懂长什么样，你只改 prompt 内容。

【示例】看懂长什么样：

```python
# -*- coding: utf-8 -*-
from openai import OpenAI
from dotenv import load_dotenv
import os

load_dotenv()
client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com/v1",
)

# max_tokens：限制"模型这次最多输出几个 token"
# 设 10 就是想看它"话说到一半被掐断"
response = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "给我讲一个完整的冷笑话，越详细越好"}],
    max_tokens=10,  # ← 关键参数：故意设小，制造截断
)

msg = response.choices[0].message
print("输出内容：", repr(msg.content))   # repr 能看见末尾有没有被切断
print("finish_reason：", response.choices[0].finish_reason)  # stop=正常结束 / length=被 max_tokens 掐断
```

### 实验 C：上下文窗口管理 + 成本估算（约 1 小时）★★★

任务：模拟多轮对话，统计 messages 总 token 增长，写"最旧截断"策略，估算一次对话的成本。

【提示】步骤（把前面学过的东西组装起来，不写新 API）：
1. 写一个 `count_messages_tokens(messages)`：把 messages 里所有 content 拼起来，用实验 A 的函数算总 token
2. 写 `manage_history(messages, limit)`：总 token 超 `limit` 时，**从最前面开始删**（但要保底：至少留 system + 最近 2 轮），直到不超限——返回删完后的列表
3. 模拟 20 轮对话（每轮 user 随便写一句 + assistant 回一句，内容长短随意，重点是让消息数增长），每轮记录"累积总 token 数"和"manage_history 处理后的轮数"
4. 成本估算：`总成本 ≈ 输入单价 × 总输入 token + 输出单价 × 总输出 token`（单价查 DeepSeek 文档，单位通常是"元/百万 token"）

| ---- | ---------------------- | ----------- | ----------------------- | ------------------ |
| 5    | 319.5 tokens           | False       | manage_history 后剩13轮 | 0.0003             |
| 10   | 601.5 tokens           | False       | manage_history 后剩13轮 | 0.0006             |
| 20   | 845.5 tokens           | True        | manage_history 后剩13轮 | 0.0008             |

- **观察思考**：为什么"删最旧"比"删最新"合理？（提示：assistant 的某个回答，依赖的是它**之前**的上下文，不是之后的）如果最后几轮删掉了一开始的 system 人设，会怎样？
    assistant的回答依赖的是他前面的上下文 不需要依靠还没发生的上下文来提供信息 同时最新回答关联性高，最旧回答一般关联性小信息价值小 system是全局约束一旦被删除就会导致结构混乱 不按初始指令/人设回答
