## 一、概念预习（约 1.5 小时）——先看课，不迷茫

### 第一步：看吴恩达 RAG 课（集号已记入 CLAUDE.md）
- **P17 检索质量评估** ★核心：评估检索器的指标体系
  - **命中率 Hit@k**：正确答案是否出现在检索结果**前 k 名**里。出现在 = 命中。衡量"检索器有没有把答案捞上来"。`Hit@k = 命中的问题数 / 总问题数`。最常用 Hit@1（只看 top1）、Hit@3（top3 里有没有）。
  - **召回率 Recall@k**：一个问题如果**有多个正确答案**（比如"请假和报销有什么规定"同时指向两段），看 k 个结果里**捞回了几个正确答案**。`Recall@k = 捞回的相关文档数 / 总相关文档数`。
  - **MRR**（了解）：不只对错，还看"正确答案排在第几名"（排第 1 给 1 分、第 2 给 1/2、第 3 给 1/3……），衡量"不仅找到，还排得靠前"。
  - 一句话区分：**Hit 管"在不在"，Recall 管"捞回几个"，MRR 管"排多靠前"**。
- **P40 RAG 评估策略实施**：把评估做进工程——**评估集（eval set）** = 一批"问题 → 正确答案"的题；每次改检索器都重跑评估集，看指标涨没涨。改完代码要能"回归"（不把原来对的弄错）。
- **P42 定制化评估体系**：不同场景定不同指标。我们今天的场景（HR 知识库问答）就用手写的评估集 + 命中率/召回率，够用且能讲清原理。进阶（9 月）再做自动化/LLM 判分。
- **P34 大模型性能评估**（了解）：评估"回答质量"用的（答得对不对、有没有引用），和"检索质量"是两回事。今天先专注检索侧，回答侧 Day55 讲引用/防幻觉时再碰。

### 边读边想的 3 个问题
1. Hit@1 和 Hit@3 哪个更"宽松"？如果你的 RAG 管道最终把 **top-2** 拼进 prompt 喂给模型，你应该重点看 Hit@几？（提示：看几段进 prompt，就看重几段有没有命中）
    K 越大 Hit@K 越宽松 Hit@3更宽松 应该看Hit@2
2. 为什么说"只看 top1 命中率"会骗人？（提示：正确答案经常在第 2、3 名，你换一个取 top-3 的管道结果就变了）
   只看 top‑1 命中率有误导性，因为真实相关文档常常排在第 2、3 位。虽然不在第一名，但业务上取 top‑3 送入 prompt 时，这些文档依然会被大模型使用，系统实际可用。Hit@1 会把这类有效案例判为未命中，从而低估检索管道的真实性能。
3. "混合检索更好"这句话，你今天要怎么用数字证明？（提示：同一份评估集、同一个命中率公式，三路检索器各算一遍，比较数字）
    同一份评估集 同一个命中率公式 分别把关键词检索向量检索和混合检索各算一遍比较数字

### 实验 C：三路检索器打分，用数字证明混合 ≥ 单一（【提示】，核心）

**流程（复用 Day53 的 exp_b，三路各写一个 retriever 函数）**：
1. 写 `retriever_bm25(q)`：返回 BM25 排名前 k 的**文档下标**
2. 写 `retriever_vector(q)`：用 ChromaDB `col.query(n_results=8)`，返回按距离升序的文档下标
3. 写 `retriever_hybrid(q)`：BM25 + 向量各排名次 → RRF 融合 → 返回下标（Day53 的代码，包一层函数）
4. 对每个 `top_k` 取值（1 和 3），调 `evaluate` 算三路各自的命中率

**填对比表**：
| 检索器   | Hit@1   | Hit@3   | Recall@3（多答案） | 谁赢？                                 |
| -------- | ------- | ------- | ------------------ | -------------------------------------- |
| 纯 BM25  | _0.667_ | _0.833_ | _ 0.5_             | Hit@1、Hit@3、Recall 三项全部最低      |
| 纯向量   | _0.833_ | _1.0_   | _1.0_              | Hit@1 最高；Hit@3、Recall 与混合持平   |
| RRF 混合 | _0.75_  | _1.0_   | _1.0_              | Hit@3、Recall 最优；Hit@1 略低于纯向量 |

**分析（写完必答，写在表格下方）**：
- 混合 ≥ 单一吗？如果 Hit@1 混合没赢，看看是哪个问题让它输了（是"撞车题"吗）？—— 这很正常，**小库 + 小评估集，差异本来就小**，记录观察，不是失败
- 应该是撞车题纯向量理解语义更占优势 RRF混合由于混合了BM25关键词匹配不上分数过低
- 哪个问题只有一路答对？把它找出来，这就是"互补"的证据
- - **编号类关键词题目：只有 BM25 能答对**；向量检索对编号实体容易出错，证明 BM25 关键词检索的价值。
- **大白话语义转述题目：只有向量检索能答对**；BM25 字面词匹配不足，发生漏召回，证明向量语义检索的价值。
  
- 如果想看到更大差异，怎么改？**（提示：加更多"撞车题"、或往库里加 2 段无关噪音文档再测——库里噪音多了，单一检索器的命中率该掉，混合兜底）**
加更多撞车题和噪音混淆库里噪音多了，单一检索器的命中率该掉，混合兜底
> **破坏性对照（加分）**：往库里加 2 段完全无关的文档（比如"食堂菜谱""健身打卡奖励"），重测三路 Hit@1。观察：谁掉得最狠？为什么？（提示：BM25 靠字撞，无关段和问题共享的字少，反而受影响小？向量会把"放假"和"健身放松"联想到一起？—— 记录观察，这就是评估暴露问题的地方）
> 向量掉的最狠 加入这些噪音增大可匹配的词义更多掉的最狠 而关键词检索反而因为噪音与目标无关影响小

## 三、自测 5 关（晚上自查）
- **能讲**：Hit@k、Recall@k、MRR 各衡量什么？"在不在 / 捞回几个 / 排多靠前"分别对应哪个？
指标	衡量什么	对应口诀	核心含义
Hit@K	命中指标	在不在	正确文档是否出现在前 K 条结果中。只要 golden 落在 top‑K，就记命中 1；不在乎排第几。适合 RAG（只要能被塞进 Prompt 即可）。
Recall@K	召回率指标	捞回几个	针对多答案问题：top‑K里面捞到的正确文档 ÷ 全部正确文档总数。衡量有多少份正确资料被找回来了。
MRR	平均倒数排名	排多靠前	看正确文档排在第几名。正确文档越靠前，分数越高；如果不在返回列表，记 0。适合搜索场景（用户优先看第一条结果）。

- **能写**：默写 `evaluate` 的最小版（单答案版本：`hits/总问题数`）
- hits=0 recall=[] 
- for q,golden in eval_set:
  - ranked=retriever(q) top_k_ranked=ranked[:top_k] if isinstance(golden,int):if golden in top_k_ranked:hits+=1 else:r=len(set(golden)&set(top_k_ranked) if r==1.0:hits+=1 recall.append(r))
- hits_rate=hits/len(eval_set)
- avg_call=(sum(recalls)/len(recalls) if recalls else 0.0)
- return hits_rate,avg_hits
- **能修**：命中率一直是 0，先查哪几处？（golden 下标标错 / 检索器返回的是字符串没转下标 / 排名顺序搞反了——BM25 降序、向量 L2 升序？）
- golden下标有问题 检索器返回的是字符串 排名顺序搞反
- **能答 why**：为什么你的 RAG 管道取 top-2 进 prompt，评估却要同时看 Hit@1 和 Hit@3？（提示：看 top-2 只关心前 2，但 Hit@3 能看出"答案稳不稳"，防止第 2 名偶尔飘）
- Hit@3 能看出"答案稳不稳"，防止第 2 名偶尔飘 答案通常在2-3名
- **能扛边界**：真实项目有 10 万段文档、1000 个评估问题，谁来标这 1000 个 golden？（提示：人工标太贵 → 抽样标注 / 用已有问答日志 / 先小评估集起步）
> 全部人工标注 1000 个 golden 成本太高。工程上一般：

1. 从真实业务问答日志抽样，对抽样样本人工标注 golden；
2. 复用线上历史用户提问、工单，仅补标 golden；
3. 先从小规模评估集迭代调参，后期再扩充；
4. 可由大模型辅助生成候选评估样本，但 golden 必须人工校验，不能直接采信 LLM 输出。
